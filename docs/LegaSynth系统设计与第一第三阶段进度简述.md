# LegaSynth 系统设计与全部模块进度简述

> 更新日期：2026-07-20  
> 本文采用 [`三阶段职责边界.md`](三阶段职责边界.md) 冻结的工作流：第一阶段完成规划、心音素材、MuseCoco主题生成及主题MIDI修正；第二阶段生成心跳鼓轨、装配完整MIDI并执行MIDI-GPT；第三阶段只统一渲染混音完整MIDI。

## 一、系统目标

LegaSynth 的目标是把数字听诊器记录的患者心音融入原创音乐。系统既要保留患者 S1、S2 的真实音色和纪念意义，也要让心跳在速度、拍号、密度和段落安排上服从音乐结构。为此，系统不让大模型直接修改心音波形，而是由大模型规划音乐意图，再由确定性的 Python 程序完成音频检测、事件移动、MIDI 坐标换算、渲染和审计。

系统接收两类输入：患者原始心音 WAV，以及用户提供的故事或音乐要求。最终输出包括完整多轨 MIDI、由真实 S1/S2 渲染的心跳音轨、混合后的音乐音频和可追溯的处理记录。

## 二、总体设计

### 第一阶段：规划与素材准备

第一阶段包含两条并行链路。

故事链由唯一的规划 LLM 读取故事，在一次运行中决定曲式、段落长度、BPM、拍号、主题家族、张力、鼓轨脉冲以及MIDI-GPT编辑范围。Python校验计划后调用MuseCoco生成主题动机，并在第一阶段内完成主题MIDI的速度、调性和小节长度修正。

心音链读取患者原始 WAV，自动选择稳定区间，检测并筛选 S1/S2 周期，以 `regularized_events_enhanced` 为标准素材。用户或 LLM 再通过 `rhythm_plan.json` 指定 BPM、拍号和 S1/S2 排列，程序据此生成可复用的 `heartbeat_package`。这个包包含真实 S1/S2 样本、心跳小节 WAV/MIDI、事件 CSV、时间—能量图、规范化计划和哈希清单。

### 第二阶段：心跳鼓轨、完整MIDI与MIDI-GPT

确定性的框架装配程序读取第一阶段已经生成和修正的主题动机，按曲式、小节坐标和轨道规则放置素材，并根据Agent鼓轨指令生成完整心跳鼓轨。随后把全部固定上下文编译为MIDI-GPT输入；MIDI-GPT只补全明确开放的伴奏、和声、低音、过渡和延伸区域。

这一阶段不混合最终音频，但必须输出已经包含完整心跳鼓轨的多轨MIDI，并保护心跳鼓轨不被MIDI-GPT破坏。

目前第二阶段已经完成一个可用的 MIDI-GPT 补全版本，也已经完成把 A、B 段拼接并加入打击乐的混音流程。现阶段的重点不再是验证流程能否运行，而是继续优化 MIDI-GPT 的补全结果，使旋律衔接、伴奏、和声、配器和段落情绪更自然、更好听并且更贴合第一阶段要求。

### 第三阶段：完整MIDI统一渲染与混音

第三阶段在MIDI-GPT完成之后运行，但不重新生成心跳鼓轨。程序读取Stage 2已经完成的整首多轨MIDI，为普通轨道分配乐器音源，为既有心跳鼓轨分配第一阶段准备的真实心音采样或SoundFont，然后把全部轨道作为一个整体渲染混音。

第三阶段不采用“先生成独立心跳WAV，再与主音乐WAV自动叠加”的流程。心跳轨和其他音乐轨在完整MIDI层面一起进入音源渲染、声像、音量、峰值和最终输出处理。

## 三、运行环境

- Windows `D:` 工作区保存正式的 Python 编排、心音处理、测试和文档。
- WSL 保存 Linux 模型运行环境；当前不仅有 MuseCoco/AMG，也存在 MIDI-GPT 模型缓存和实验脚本。
- DeepSeek 故事规划通过 API 调用，不依赖 WSL 中的本地大模型。
- Windows 工作区在 WSL 中可通过 `/mnt/d/...` 访问，但这只是挂载，不代表项目文件被复制到 WSL 虚拟磁盘。

## 五、第一阶段当前进度

### 已完成

1. `heart_extraction` 已能自动测算 stable 区间，检测 S1/S2，筛选周期，并输出 Stable、Authentic、Regularized 三组不同保真度的音频及时间—能量图。
2. `heartbeat_stage1` 已形成统一入口，可从原始 WAV 直接生成 `regularized_events_enhanced` 和便携的 `heartbeat_package`。
3. S1/S2 的目标 BPM、拍号、事件位置、重复方式和力度可由用户或 LLM 通过严格 JSON 指定；程序拒绝时间拉伸、变调和未经允许的动态压缩。
4. 真实样本 `202607071630425298.wav` 已完成端到端验证，成功生成 103.15 BPM、4/4 拍、8 个 S1/S2 事件的心跳小节。
5. 第一阶段心音总入口的 4 项直接测试全部通过；连同心音提取和节拍渲染相关回归，共核验 25 项测试。
6. `stage1_story_agent` 已能生成相互隔离的 MuseCoco 计划、`stage2_plan.json`、`heartbeat_processing_plan.json` 和审计文件；阶段末现可强制统一 MuseCoco MIDI 的 BPM 和主音，并在调式不一致时拒绝进入第二阶段。当前 90 项离线测试通过，此前 2 项真实 DeepSeek 集成测试通过。

### 当前边界

第一阶段负责准备真实心音素材、主题动机及其规范化结果。Agent的逐段鼓轨指令由Stage 2消费，用于生成完整心跳鼓轨；不得延迟到Stage 3重新生成。

## 六、第二阶段当前进度

### 已完成

1. MIDI-GPT 音乐补全已经形成可运行、可产出结果的版本。
2. A、B 段的拼接流程已经完成。
3. 打击乐已经能够加入 MIDI；下一步是按 `stage2_plan.json` 在 Stage 2 固化为完整心跳鼓轨，并在 MIDI-GPT 前后验证受保护事件不变。
4. 第一阶段到第二阶段的主要控制信息已经明确，包括段落长度、BPM、拍号、张力、鼓型以及 MIDI-GPT 的保护和可编辑区域。

### 正在优化

当前主要问题是“生成质量”，而不是“流程连通性”。后续优化应重点考察：

1. A、B 段之间的旋律、和声与配器衔接是否自然；
2. MIDI-GPT 新增内容是否延续主题动机，而不是产生无关材料；
3. 伴奏密度、低音、和声与打击乐是否符合段落张力；
4. 生成结果是否遵守第一阶段规定的 BPM、拍号、段落长度和保护区域；
5. 是否能通过候选生成、规则评分和人工试听，从多个结果中选择更符合要求的版本。

因此，第二阶段目前应表述为：**端到端可用版本和基础混音已经完成，正在进入 MIDI-GPT 音乐性与条件一致性优化阶段。**

## 七、第三阶段职责

### 已具备的基础

1. 输入必须是Stage 2已经生成完整心跳鼓轨的整首多轨MIDI。
2. 第一阶段准备的真实S1/S2采样或SoundFont只作为心跳鼓轨音源。
3. 普通轨和心跳轨在同一个MIDI工程中统一渲染、混音和输出。
4. 第三阶段不重新规划、生成或校正心跳鼓点。

当前需要固化的是“完整MIDI统一音源分配与混音”入口及其验收标准，而不是后置心跳重生成器。`heartbeat_post_renderer`实验不计入第三阶段完成度。

## 八、下一步

近期工作应先把当前Agent的`stage2_plan.json`接入Stage 2框架装配器，确保它生成并保护完整心跳鼓轨；随后为Stage 3固化完整MIDI的统一音源渲染、混音和验收流程。
