# 3 方法

## 3.1 系统总体架构

本系统将自然语言叙事与患者真实心音结合，生成包含可辨识心跳音色的完整音乐。系统的外部输入为故事文本、数字听诊器录制的心音 WAV，以及可选的用户音乐约束。曲式、心跳节奏和混音参数并非彼此独立的外部输入，而是由第一阶段的规划结果经确定性程序校验、派生和编译形成的内部控制产物；在测试模式中，部分参数可由固定模板提供。

系统采用三个阶段。Stage 1 负责故事规划、主题动机生成和心音素材准备；Stage 2 负责完整 MIDI 的装配与补全；Stage 3 负责音源映射、音频渲染、心跳响度平衡和最终母带处理。阶段之间通过带有 Schema、文件哈希和来源信息的机器可读清单交接，以避免复用其他任务的中间产物。

## 3.2 Stage 1：规划、主题生成与心音素材准备

### 3.2.1 Story Planning Agent

Story Planning Agent 通过 DeepSeek API 访问托管大语言模型，将自然语言故事转换为结构化音乐计划 \cite{deepseek_api}。Agent 分析叙事事件、情绪变化、张力和内容上的再现关系，并据此规划段落结构、主题家族、速度、拍号、全局调性以及各段落的音乐表达要求。系统不强制采用固定 ABA 曲式；内容上的重现可以引用已有主题家族，而新的叙事材料则建立新的主题家族。

模型输出不会直接作为下游程序的自由文本指令。Python 校验层按照预定义 Schema 检查字段、取值范围、段落边界和主题引用关系，再将有效规划编译为内部控制产物，包括音乐结构计划、心跳处理与编排参数以及 Stage 3 音频渲染参数。测试模式使用相同的处理链，但以固定曲式、段落长度、速度和调性约束替代相应的自由规划字段。

### 3.2.2 MuseCoco 主题生成

对于每个新的主题家族，Stage 1 将规划结果映射为 MuseCoco 的结构化音乐属性。项目绕过 MuseCoco 原有的 text-to-attribute 模型，以确定性的 one-hot 编码直接构造其官方属性空间输入，但保留未修改的官方预处理程序与 attribute-to-music 生成模型 \cite{musecoco}。每个主题作为独立任务进入 WSL 队列，以避免不同任务之间共享临时状态。

MuseCoco 输出经项目外部 wrapper 后处理。系统将主题裁剪为准确的八小节边界、统一计划 BPM，并根据所选策略处理调性。在严格模式下，系统检测生成结果并将其修正到计划规定的主音和调式；在宽松模式下则保留模型原始调性。最终交付给 Stage 2 的是经过长度、速度、调性和文件哈希校验的主题 MIDI，而不是 MuseCoco 的原始临时结果。

### 3.2.3 心音提取与素材构建

心音处理链从单声道 WAV 中计算波形包络、短时能量和周期性特征，自动定位质量较稳定的时间区间，并在其中检测交替出现的 S1/S2 事件。候选区间依据周期一致性、事件能量和噪声水平进行评分，从而选择适合循环使用的真实心音事件。该流程是本项目实现的确定性启发式处理链，并非对既有统计或深度学习心音分割模型的复现；相关噪声鲁棒心音分割工作仅作为方法背景 \cite{arjoune2024noise}。

基础素材构建包括事件感知的谱减法、背景衰减、包络压缩、响度提升和峰值保护，其目标是形成干净、稳定且可复用的 S1/S2 素材库。预处理完成后，节奏构建只调整完整事件的时间位置和线性增益，不对单个 S1/S2 样本进行时间拉伸或移调，因而尽量保留患者原始心音的内部结构和音色。

Stage 1 根据内部节奏参数生成单小节心跳音频素材及符号化 MIDI 事件模板，并将原始片段、增强片段、S1/S2 标签、对齐偏移、质量分数和文件哈希封装为 `heartbeat_package`。该素材包在 Stage 3 中用于将符号化心跳事件恢复为真实录音音色。

## 3.3 Stage 2：MIDI 装配与生成式补全

### 3.3.1 曲式与主题装配器

Stage 2 首先由确定性的 Python 装配器读取 Stage 1 的结构计划和主题清单。装配器按照段落及小节坐标放置主题 MIDI，并依据主题家族关系实现首次陈述、再现、变奏或发展。正式模式不假定固定曲式或固定总长度；每个段落通常由八小节主题和默认八小节填充区组成，但实际曲式顺序由 Stage 1 计划决定。

装配器在填入项目心跳轨之前，强制移除输入 MIDI 中已有的 General MIDI percussion channel 10 事件（从 1 开始计数；在程序中对应通道索引 9），避免 MuseCoco 或历史素材中的鼓事件与计划心跳发生冲突。

### 3.3.2 心跳事件轨与保护区域

装配器根据 Stage 1 为各段规定的 S1/S2 排列、拍内位置和素材选择规则，确定性地构造完整歌曲的心跳事件轨。该轨使用 General MIDI percussion channel 10 中约定的音符表示 S1 和 S2，并与固定主题区域共同标记为受保护内容。

心跳轨在 MIDI-GPT 推理期间保持可见，作为其他音乐轨的节奏上下文，但其目标小节列表为空，因此模型不能在该轨上生成或覆盖事件。每次补全后，wrapper 比较推理前后的心跳事件签名；只要事件时间、音高、速度或持续时间发生变化，本次结果即被拒绝。

### 3.3.3 MIDI-GPT 补全适配器

MIDI-GPT 用于对计划允许编辑的旋律、和声、低音、伴奏和过渡区域进行 bar-level infilling \cite{midigpt}。项目 wrapper 将整曲划分为较短的连续补全块，为当前活动音乐轨建立 `TrackPrompt`，并将已经完成的结果立即写回工作乐谱，使后续补全能够利用前文上下文。与当前段落无关的音乐轨在该次请求中被隐藏，以减少不同主题与配器之间的相互干扰。

分块写回、检查点保存、受保护事件验证、失败重采样和结果合并均由本项目 wrapper 实现，而不是 MIDI-GPT 的原生功能。Stage 2 输出的是已经包含心跳事件轨的完整多轨 MIDI，而不是独立的音乐 MIDI 与心跳音频。

### 3.3.4 输出后处理

当最后一个可编辑区域覆盖整曲结尾且至少包含两个小节时，wrapper 从现有非打击乐轨重新估计调性，并将最后两个可编辑小节确定性地改写为 V–I 或 V–i 终止式，以降低突然结束的听感。该终止式依据的是对当前 MIDI 内容的重新估计，而不是直接读取 Stage 1 的计划调性。

系统另提供由用户显式选择的整体重复检测与局部再生成模块。该模块比较相邻两小节的整体有音高织体，不区分旋律与和声，也不将固定节奏视为重复惩罚；由于它不是默认生成链的必要步骤，具体阈值和重试策略置于附录说明。

## 3.4 Stage 3：统一渲染与自适应混音

### 3.4.1 音源映射与心跳播放适配

Stage 3 接收 Stage 2 输出的完整 MIDI、一个或多个 `heartbeat_package` 以及内部渲染计划。普通音乐轨通过 FluidSynth 和 GeneralUser GS SoundFont 渲染 \cite{fluidsynth,generaluser_gs}。心跳通道不使用通用鼓音色；系统将 S1/S2 MIDI 事件解释为时间与类型标记，并从选定素材包中放置对应的真实 S1/S2 样本。多个素材包可以按计划固定选择或轮换，但事件时序仍由 Stage 2 的 MIDI 决定。

Heartbeat Conditioning 以 Stage 1 已增强的样本为输入，执行面向当前混音和普通播放设备的带限滤波、动态压缩、短淡入淡出与峰值归一化。该模块不会重复 Stage 1 的谱减法降噪：Stage 1 的动态处理用于建立干净稳定的基础素材库，Stage 3 的动态处理则用于适应当前音乐背景和播放条件。

### 3.4.2 逐事件响度平衡

系统先独立渲染普通音乐，并依据 MIDI 时间轴放置心跳事件。对于第 \(i\) 个事件，在其有效时间窗内分别计算音乐和心跳的 K-weighted 事件级感知电平 \(L_{m,i}\) 与 \(L_{h,i}\)。这些短窗测量不称为 integrated LUFS；BS.1770 风格的整曲积分响度仅用于最终母带阶段 \cite{itu_bs1770}。

若目标心跳相对音乐的电平差为 \(\Delta\)，请求增益定义为：

\[
G_{i,\mathrm{req}}^{\mathrm{dB}}
=L_{m,i}-L_{h,i}+\Delta.
\]

请求增益先被限制在允许范围内，再对连续同类事件施加最大增益变化约束。记经过上下限约束和同类 S1/S2 事件连续性平滑后的最终增益为 \(G_i^{\mathrm{dB}}\)，其线性增益为：

\[
g_i=10^{G_i^{\mathrm{dB}}/20}.
\]

当允许的心跳增益仍不足以达到目标相对电平时，系统只在对应心跳事件附近生成 attack–hold–release 音乐闪避包络，而不降低整首音乐的电平。该策略优先保持真实心音的音色，同时减少突发增益、削波和全局音乐响度下降。

### 3.4.3 最终母带与审计

音乐与心跳完成逐事件平衡后，系统计算合成信号的整曲积分响度，并使用四倍过采样估计真峰值。单一母带增益由合成后的总混音计算，并相同地施加到音乐与心跳分轨后再进行最终求和；因此，逐事件平衡阶段建立的相对响度关系不会被改变。母带增益同时受目标 LUFS 和真峰值上限约束。

Stage 3 输出最终 WAV，并可选输出音乐与心跳诊断分轨。审计文件记录每个心跳事件的素材来源、事件级测量值、最终增益、局部闪避量、母带响度、真峰值估计和输入输出哈希。

## 3.5 实现与可追溯性

系统控制、MIDI 处理和数字信号处理模块使用 Python 实现，数值计算主要依赖 NumPy 和 SciPy \cite{harris2020numpy,virtanen2020scipy}。Stage 1 的 MuseCoco 推理运行在 WSL 环境中；Stage 2 的 MIDI-GPT 通过独立的 Windows Python 环境运行；Stage 3 使用 FluidSynth 完成普通音乐轨渲染。

每次任务保存结构化计划、模型提供方与模型标识、提示词版本、随机种子、中间文件、阶段日志和输入输出 SHA-256。这些记录支持流程追溯和部分可复现性，但由于托管语言模型和生成模型的运行环境可能发生变化，系统不声称能够对所有任务进行逐比特完全复现。
