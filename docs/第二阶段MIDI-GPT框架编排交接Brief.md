# 第二阶段 MIDI-GPT 框架编排交接 Brief

> 2026-07-20 职责更正：以 [`三阶段职责边界.md`](三阶段职责边界.md) 为权威。第二阶段读取 `*-stage2/stage2_plan.json`，生成完整心跳鼓轨、组装完整多轨 MIDI，并执行 MIDI-GPT 填充与保护校验。`*-heartbeat/heartbeat_processing_plan.json` 当前只作为兼容/审计视图；不得在 MIDI-GPT 完成后据此重新生成心跳事件。Stage 3 只对已经包含心跳鼓轨的完整 MIDI 统一渲染混音。下文与此冲突的内容均为旧实现说明。

> 面向接手开发者的简明说明。具体字段和参数请查链接文档，不在本 Brief 重复展开。

## 这部分解决什么问题

项目不会把故事、心音或零散动机直接交给 MIDI-GPT。第一阶段唯一的规划 LLM 已经形成清晰音乐蓝图；第二阶段只由确定性程序把蓝图、实际心音事件和实际动机编译成 MIDI-GPT 能理解的多轨框架。

整个过程分工如下：

- 第一阶段唯一 Agent 根据故事同时决定曲式分段、每段小节数、主题家族、动机放置、逐段心音方案和 MIDI-GPT 填充区域；
- Stage 1 调用 MuseCoco 产生新主题素材，并统一主题 MIDI 的速度、调性和小节长度；
- 第二阶段没有 LLM；框架装配器执行第一阶段决定，保护心音和主题，不自行猜测音乐意图；
- MIDI-GPT 只补全明确开放的区域；
- 推理完成后再验证受保护内容没有被改写。

段落长度和编排意图的权威是第一阶段 LLM 输出。Python 只检查各段长度是否满足用户给出的总量和上下游约束，再依次计算起止位置并绑定实际素材；它不得平均分段、套用示例曲式或擅自增减任何一段。

## 当前已经完成

`midigpt_scaffold_builder` 的离线编译核心已经完成，可以：

- 读取第一阶段同次规划生成的内容计划、音乐计划，以及后续产生的心音事件和动机清单；
- 检查段落、小节、轨道和素材引用是否一致；
- 逐段编排心音并放置主题动机；
- 区分受保护内容、生成区域和不参与模型上下文的辅助轨；
- 生成 MIDI-GPT 所需的结构化输入、可视 MIDI 和审计报告；
- 生成可直接交给 HTTP 服务的组合请求；
- 在真实 checkpoint 加载后调用 MIDI-GPT 自身的校验器做最后确认。

受保护音符现在会完整保留；如果素材本身越过声明边界，程序会明确报错，不再静默裁短。

## 当前还没有完成

- MuseCoco 适配器还没有把主题请求变成正式动机清单；
- 第一阶段 Agent 当前只生成 `content_plan.json`，尚需在同一次规划中增加符合装配器 Schema 的 `music_plan.json`；
- MIDI-GPT 推理适配器还没有真正加载模型并生成整曲；
- 生成后保护事件比较和最终音频渲染还没有接入；
- 第一阶段分消费者规划、MuseCoco 旋律硬约束、张力驱动鼓轨脉冲及 MIDI 强制速度/主音修正现已通过 90 项离线测试；此前 2 项真实 DeepSeek 集成测试通过。第二阶段只能接收已通过 `normalize-tempo` 和 `normalize-key` 的主题 MIDI，并且只消费鼓轨脉冲，不消费 S1/S2 音频或心音标签。

## 接手后建议顺序

1. 先跑离线测试，确认工作区基线；
2. 扩展第一阶段同一个 Agent，使其在一次规划运行中原子输出 `content_plan.json` 和 `music_plan.json`；
3. 完成 MuseCoco 动机清单，使每个主题都可追溯；
4. 用合成素材跑通完整装配流程；
5. 在独立环境加载固定 MIDI-GPT checkpoint，先做契约校验，再做小规模推理；
6. 增加生成前后保护内容比较；
7. 最后处理音色、混音和整曲质量。

## 不要破坏的原则

- 全流程只有一个规划 LLM，位于第一阶段；不得在本阶段新建第二个 LLM 或让其根据实际素材重新规划；
- 第一阶段 LLM 决定曲式分段、每段小节数和音乐意图；Python 只据此计算坐标、执行放置并检测错误；
- 心音和已批准主题默认是锚点，不是随意重写区域；
- 所有生成区域必须显式声明；
- 项目计划字段不能冒充 MIDI-GPT 官方字段；
- checkpoint 专属能力必须运行时读取，不能由 LLM 猜测；
- 所有素材和结果都应保留来源、版本和哈希。
